## [EVM-L1] Repeated tiny income allocations bias equal plugin weights toward the last plugin
**Severity**: Low
**Category**: evm-audit-precision-math
**Location**: `SingleSparkContract/chains/evm/gameplay/GameplayVault.sol:163`, `_allocate()`; inherited by `PonsGameplayVault`.
**Description**: Each sync independently floors the shares of every enabled plugin except the last historical ID, which receives all remaining funding units. Carrying platform/Claim/work fractions across events does not carry individual plugin fractions. With equal weights, many income events below the plugin-count quantum therefore allocate all work funds to the last plugin. This is explicitly described by `docs/evm/protocol.md:51`; the finding concerns the cumulative economic consequence of that policy. The error per event is fewer than `(enabledPluginCount - 1)` funding base units, so the current native-ETH Pons path has only dust-scale impact. Coarse-unit assets in future shared EVM integrations could experience material skew. No profitable extraction path or spending beyond project budgets was demonstrated.
**Proof of Concept**: Added `SingleSparkContract/chains/evm/gameplay/test/GameplayAllocationAudit.t.sol:9`. Create two Vaults using the existing fixture, same six-decimal funding token and weights `1:1:1`. Fund one 200 times with 1 raw unit, and fund the other once with 200 units. Both hold 200 units, reserve platform=20 and Claim=1, and allocate 179 work units. Split-income budgets are `0/0/179`; bulk-income budgets are `59/59/61`. Command: `forge test --root SingleSparkContract/chains/evm --match-contract GameplayAllocationAuditTest --out /tmp/singlespark-audit-skills/evm-audit-out --cache-path /tmp/singlespark-audit-skills/evm-audit-cache -vv`. Actual result: compiler success; **1 passed, 0 failed, 0 skipped**.
**Recommendation**: If weights are intended to describe cumulative revenue shares, preserve per-plugin fractional allocation across events under each active weight configuration, while keeping existing budgets immutable across policy changes. Otherwise explicitly accept this base-unit bias and exclude coarse-unit funding assets whose normal income events would make it significant. No on-chain deployment or correction was performed.

## Reviewed security boundaries

- `GameplayVault`, `GameplayVaultFactory`, `GameplayPlugins`, `GameplayAsset`, `IGameplayProtocol` and `GameplayV4Adapter` were read in full. Factory-only initialization locks the implementation; deterministic clones initialize atomically. Registry code hashes, immutable distinct admin/authorizer roles, bounded callbacks and per-project/per-plugin ledgers prevent arbitrary online-role withdrawals. Claims bind caller, chain, Vault, amount, minimum output, reward, deadline, nonce, policy/registry revisions and data hash. Nonce is consumed before external execution; all failures revert atomically.
- The pre-existing source carry preserves top-level 10%/0.5%/89.5% fractions and an unspendable rounding reserve. Same-asset inventory remains in accounted funding without being resynced as revenue; cross-asset spending requires exact input and output balance changes. Reward reservation is released proportionally only on actual distribution. Restricted/taxed token failures do not partially advance paid flags or spending.
- V4 validates initialized matching pools, bounded signed exact-input amounts, authenticated hash-bound PoolManager callbacks, full input consumption, nonzero signed minimum output and deadlines. Pons additionally pins source/hook/manager hashes, expected curve/token/factory/native pairing and pool key. Native curve and graduated V4 paths enforce output. Existing real-V4 tests cover high creator-tax net quotes, not merely mocked swap success.
- Local/global pause revises authorization state; pending earlier policy/resume operations are invalidated. Policy/plugin/adapter/resumption activations use 48 hours in production source. `build-gameplay.mjs:42-44` substitutes 10 minutes in compiler input only for the chain-46630 isolated test build and freezes artifacts against signed journals.
- Pons repeated recipients within and across batches are explicitly authorized workspace policy, not a finding. Sorted recipients, address exclusions, nonce/data/signature checks and isolated budgets remain enforced. Shared EVM permanent policy remains unchanged.
- `PlatformNft`, `PlatformNftRevenueVault`, `PlatformNftVaultFactory` and their interface were read in full. Platform collection and ledgers are independent of Pons. Mint commands have a 48-hour queue and consumed operation flags. NFT staking checks ownership and immutable quality, uses bounded batches, records account/global integral checkpoints, and preserves historical weights after exit. Historical epoch settlement uses binary search and per-account claim flags; failed or duplicate batches revert. Owner withdraws only its cumulative 50% ledger. Empty-cycle rollover remains NFT money. Pausing blocks new staking/minting while exit and earned claims remain available.
- Reviewed existing tests for replay/cross-chain/cross-Vault protection, plugin boundaries, pending-operation invalidation, exact transfer handling, inventory reward release, V4 swaps, repeated Pons recipient policy, historical NFT epochs, forced income, empty rollover, duplicate claims and callback reentrancy. Root owns full-suite results and automated Slither output; this report adds only the targeted reproduction result above.

## Deployment and coverage limits

- `docs/robinhood/pons.md:103-105` explicitly distinguishes current repeat-policy source from pinned immutable permanent-policy Vaults. New fee-carry source similarly does not update existing bytecode. Public JSON was inspected as recorded evidence; no live RPC/code-hash re-verification or funds movement was performed by this agent.
- Platform NFT public `nft-vault.json` records verified testnet deployment with 48-hour delay, 7-day epochs, and `weeklyClaimLiveVerified: false`. Local epoch tests do not establish a completed live weekly claim.
- External Pons/Uniswap/OpenZeppelin code was treated as dependency behavior bounded by the reviewed adapters/pins; it was not comprehensively re-audited. Backend/frontend signing eligibility, real-wallet browser flows, MEV economics, infrastructure and chain consensus were outside this assigned contract review. ARC/Argus and Solana are covered by separate agents.
- Ordinary floor-rounded NFT claims can leave fewer than one base unit per claimant per epoch in `nftReserve`; this does not overpay another account or let the owner take NFT funds and was treated as bounded arithmetic dust, not a separate security vulnerability.
